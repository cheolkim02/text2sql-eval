# AI와 함께 개발한 방식

이 저장소는 2026-11-03부터 11-15(v0.1.0 배포)까지 Claude Code와 함께 만들었다. 이 문서는 사람과 AI가 일을 어떻게 나눴는지, AI를 어떻게 통제했는지, AI가 어디서 틀렸고 그것을 어떻게 잡았는지를 정리한다. 날짜별 기록은 [개발 기록](dev-log/), 결정 하나하나는 [결정 기록](decisions/README.md)에 있다.

## 역할

[AGENTS.md](../AGENTS.md)에 정해 두고, Claude Code가 세션마다 읽게 했다([CLAUDE.md](../CLAUDE.md)가 불러온다).

| 사람 | Claude |
| --- | --- |
| 설계와 결정, diff 리뷰, merge 지시 | 선택지 조사와 추천, 구현, 테스트, 문서 초안, 기록 |

사람은 이 저장소의 모든 줄을 설명할 수 있어야 한다. 그래서 빨리 많이 쓰는 것보다, 사람이 이해할 수 있게 작게 나눠 쓰는 것을 우선했다.

## 장치

**결정은 사람이 한다.** 공개 API, 의존성, 설정 파일, 파일 형식, 판정·차이·플래그 규칙, 폴더 구조, 도구 선택은 모두 결정 대상이다.

- **묻는 형식:** 이런 결정이 필요하면 Claude는 구현을 멈추고 정해진 형식으로 묻는다.
  - 맥락
  - 선택지 2~4개의 장단점 표
  - 추천과 이유. 도구라면 확인한 공식 문서나 PyPI 링크도 붙인다.
- **기록:** 사람이 답하면 그 자리에서 [ADR](decisions/0000-template.md)을 쓴다. ADR에는 결정 이유를 적고, 추천을 고르지 않았으면 그 사실도 적는다.
- **Claude가 혼자 정하는 것:** 함수 이름이나 코드 배치처럼 밖에서 보이지 않는 것만 정하고, 커밋 본문에 남긴다.

**기능 하나는 이 순서로 만든다.**

1. Claude가 계획을 3~5줄로 제시하고 사람이 승인한다.
2. 테스트를 함께 쓰고, 실패 경로도 테스트한다.
3. `sh scripts/check.sh`(Ruff, pyright strict, pytest)를 통과시킨다.
4. Claude가 자가 검토 체크리스트로 검토하고, 고친 것과 남은 것을 보고한다.
5. PR을 만들고, CI가 모두 통과하면 사람의 지시로 merge한다.

**스킬 4개** ([.claude/skills/](../.claude/skills/)):

| 스킬 | 언제 | 하는 일 |
| --- | --- | --- |
| `decide` | 결정이 필요할 때 Claude가 스스로 | 위 형식으로 묻고, 답을 받으면 ADR·색인·PLAN을 갱신 |
| `review` | 구현을 마칠 때 Claude가 스스로 | 타입, 테스트, 의존성, 결정성, 오류 메시지 체크리스트로 자가 검토 |
| `explain` | 사람이 `/explain <경로>`로 | 코드를 설명하고 질문으로 이해를 확인. 문답은 공개하지 않는 `.study/`에 저장 |
| `devlog` | 사람이 `/devlog`로 | 그날의 개발 기록. "AI가 틀린 것"을 부풀리지 않고 적는다 |

**기록으로 남긴다.** Claude가 함께 쓴 커밋에는 `Co-Authored-By` 줄을 붙였다. 이미 push한 커밋은 고치지 않았다.

**만들지 않은 것.** 계획에는 Claude가 응답을 끝낼 때마다 "결정 기록 없이 의존성·형식이 바뀌었는지" 검사하는 Stop 훅(`scripts/check_decisions.py`)이 있었다. 일정이 늦어져 [ADR 0012](decisions/0012-schedule-adjustment-1107.md)에서 권장 범위로 내렸고, 만들지 않았다. 결정 기록은 규칙과 `decide` 스킬로만 지켰다.

## 사람이 바꾼 것

**기각한 추천.** 추천과 다른 결정을 내린 이유는 ADR에 남아 있다.

- **Ruff 규칙 세트** ([0015](decisions/0015-ruff-default-rules.md)): Claude는 넓게 고른 규칙 세트를 추천했다.
  > "처음 만들어보는 거니까, 품질이 좀 떨어지더라도, 명백한 실수만 잡아보도록 하자."
- **통계 검정** ([0035](decisions/0035-no-significance-test.md)): Claude는 실행 비교에 McNemar 정확 검정을 직접 구현하자고 추천했다.
  > "McNemar는 내가 써본것도 아니고, 이게 실제 nl2sql 연구 평가에서 중요하지 않는 부분 같아서, 이건 안하고 싶은데"
- **baseline 모델** ([0030](decisions/0030-baseline-model-gpt-4o-mini.md)): Claude는 gpt-5.4-mini를 추천했다. 사람은 gpt-4o-mini를 골랐고, 지원 중단 예정이라는 말을 들은 뒤에도 그대로 정했다.
- **HTML 리포트 범위** ([0039](decisions/0039-html-report-scope.md)): Claude는 기본 화면만 추천했다. 사람은 다른 절과 행의 색칠까지 넣었다.

**설계를 직접 고친 것.** 오답 분석(대표 기능)의 모양은 사람이 실제 오답을 함께 읽으며 정했다.

- [0031](decisions/0031-error-facts-v1.md): Claude가 오답 161건을 분류해 카테고리 7개를 제안하자, 사람은 이렇게 답했다. 이에 따라 카테고리를 5개로 줄이고 SQL 구조 비교를 앞당겼다.
  > "이 7개에서 3,4 합치고, 6,7 합쳐. Sql 구조도 지금 하자."
- [0033](decisions/0033-multi-label-differences.md): 첫 구현을 본 뒤 사람이 이렇게 요청했다. 이에 따라 오답 하나에 차이 여러 개를 붙이는 다중 라벨로 바꾸고, 컬럼 차이를 더했다.
  > "오답마다 하나 이상의 카테고리가 있을 수 있고, 잘못된 테이블 혹은 잘못된 컬럼 사용도 있으면 좋겠어."

## AI가 틀린 것: 대표 사례 3개

전체 목록은 [개발 기록](dev-log/2026-11-13.md#ai가-틀린-것과-고친-것)에 있다. 이 기간에 코드 오류는 대부분 도구(pyright, 테스트, CI)나 Claude 자신의 실측과 재확인에서 잡혔다.

### 1. 그럴듯했지만 대부분 가짜였던 강조 규칙

- **무엇이 틀렸나:** HTML 리포트는 정답·예측 SQL에서 다른 절을 칠한다. 승인된 계획은 SQL 구조 차이와 같은 정규화(별칭, 대소문자, 테이블 이름)를 한 뒤 같은 절끼리 글자를 비교하는 것이었다. 그대로 구현하니 테스트는 통과했다.
- **어떻게 알았나:** 보고하기 전에 Claude가 커밋된 실행에서 칠해진 절을 셌다. 오답 165개 중 138개에서 FROM 절이 칠해졌는데, 테이블 구성이 실제로 다른 경우는 72개뿐이었다. 사례를 읽어 보니 `INNER JOIN`과 `JOIN`, 내부 조인의 테이블 순서, `ON a = b`와 `b = a`, AND 조건의 순서 차이였다. 모두 SQLite에서는 뜻이 같다.
- **어떻게 고쳤나:**
  - 이 네 가지는 같게 보도록 비교를 바꾸고, 같게 봐야 하는 경우와 진짜 차이인 경우를 테스트로 고정했다. FROM 강조는 77개로 줄었다.
  - 계획에서 달라진 점이라 사람에게 보고하고 [ADR 0039](decisions/0039-html-report-scope.md)에 규칙을 적었다.
  - 커밋: [e119a00](https://github.com/cheolkim02/text2sql-eval/commit/e119a00)
- **배운 점:** 테스트가 통과해도 규칙이 맞는 것은 아니다. 실제 데이터에서 세어 봐야 했다.

### 2. 기계 속도를 검사하던 재현성 테스트

- **무엇이 틀렸나:** 공개한 baseline 숫자가 몰래 바뀌지 않도록, 커밋된 예측 432개를 다시 판정해 커밋된 결과와 비교하는 테스트를 만들었다. 이 컨테이너에서는 통과했다.
- **어떻게 알았나:** GitHub Actions의 Python 3.14 서버에서 실패했다(PR #8). 이 컨테이너에서 약 18초 걸리던 예측(no-evidence 247번)이 그 서버에서는 30초 제한을 넘어 "오답"이 아니라 "시간 초과"로 판정됐다. 테스트가 판정 규칙이 아니라 기계 속도를 검사하고 있었다.
- **어떻게 고쳤나:**
  - 시간 제한을 늘리거나 다시 돌리는 대신, 시간에 민감한 예측 3개(211, 247, 281)를 찾아 [결과 README](../examples/results/README.md#시간-제한에-민감한-케이스)에 적었다.
  - 재현성 테스트는 이 3개를 빼고 다시 판정하고, 3개는 기록된 판정을 별도 테스트로 고정했다.
  - 커밋: [b0eae1b](https://github.com/cheolkim02/text2sql-eval/commit/b0eae1b)
- **배운 점:** 실패한 테스트를 통과하게 만드는 것과, 테스트가 무엇을 검사해야 하는지 바로잡는 것은 다르다.

### 3. 문서의 사실 오류와, 실패하지 않던 문서 테스트

- **무엇이 틀렸나:** 레퍼런스와 가이드 초안에 그럴듯하지만 틀린 문장이 여러 개 있었다.
  - 실제 출력과 다른 오류 힌트 문구를 지어 넣었다.
  - BIRD evidence 인용이 원문과 달랐다.
  - "판정을 다루는 곳은 모두 `match`와 `assert_never`를 쓴다"고 과장했다.
  - "`Literal`에 값을 더하면 한국어 설명 표에서 빠진 것을 pyright가 잡는다"고 썼다. 실제로는 잡지 않는다.
  - 실행 파일 버전 정책을 거꾸로 썼다.
  - 원본 스크립트로 확인하지 않은 BIRD 형식 변환법을 썼다.
- **어떻게 알았나:** 커밋하기 전에 Claude가 문장마다 코드, 실제 출력, 원문과 대조했다.
  - 문서가 코드와 어긋나지 않게 하려고 만든 테스트도 일부러 문서에서 항목을 지워서 정말 실패하는지 확인했다.
  - 그러자 실행 파일 문서 검사는 실패하지 않았다. JSON 예시에 필드 이름이 들어 있어서, 설명이 빠져도 통과했던 것이다.
- **어떻게 고쳤나:**
  - 틀린 문장은 고치거나 지웠다.
  - 테스트는 설명에 `` `필드` ``로 적혀 있어야만 통과하도록 엄격하게 바꿨다. 그러자 설명이 빠진 필드 4개(`output`, `sql_structure`, `total`, `ex`)가 드러나 채웠다.
  - 커밋: [857e3b1](https://github.com/cheolkim02/text2sql-eval/commit/857e3b1), [fbb57e0](https://github.com/cheolkim02/text2sql-eval/commit/fbb57e0)
- **배운 점:** AI는 자연스러운 문장으로 사실이 아닌 것을 쓴다. 그리고 테스트는 실제로 실패하는 것을 봐야 믿을 수 있다.

## 검증 장치

AI가 쓴 코드를 믿기 위해 사람의 리뷰 말고도 이런 장치를 두었다.

- **타입:** pyright strict 0 오류. 공개 API에 `Any`가 없는지 테스트로 검사한다.
- **공식 결과와 대조:** 같은 예측을 BIRD 공식 평가 스크립트로 채점해 EX 8개 숫자가 같음을 확인했다.
- **재현성:** 커밋된 실행 파일과 HTML 리포트가 예측 파일에서 그대로 다시 나오는지 테스트한다.
- **문서:** 공개 이름, CLI 옵션, 실행 파일 필드, 링크·앵커가 코드와 맞는지 테스트한다.
- **배포물:** CI가 빌드한 wheel을 깨끗한 환경에 설치해 CLI를 실제로 돌린다([ADR 0044](decisions/0044-ci-dogfooding.md)).
- **원본 확인:** 라이브러리 API, BIRD 평가 규칙, 도구의 현재 상태는 공식 문서·원본 코드·PyPI로 확인한다. 확인하지 못한 것은 쓰지 않는다(AGENTS.md 절대 규칙 8).

## 돌아보며

- **AI의 속도와 사람의 결정:** 구현 속도는 AI가 냈다. 하지만 무엇을 만들지와 무엇을 뺄지는 사람이 정했다. 카테고리 매핑 파일과 통계 검정을 빼고, 리포트에 강조를 넣은 결정이 그 예다.
- **틀리는 방식:** AI는 코드보다 규칙과 문장에서 더 그럴듯하게 틀렸다. 그래서 실측(세어 보기)과 원문 대조가 가장 효과적인 통제 수단이었다.
- **사람의 이해:** 사람이 모든 줄을 설명할 수 있도록 모듈마다 `/explain`으로 복습한다. 문답은 공개하지 않는 `.study/`에 남긴다.
