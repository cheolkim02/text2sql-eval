## AI가 틀린 것과 고친 것

누가 또는 무엇이 발견했는지를 함께 적는다. 이 기간에 사용자가 직접 찾아낸 코드 오류는 없었다. 사용자는 설계를 바꾸고(0031, 0033) 추천을 기각했다(0030, 0035, 0039).

**지어낸 것, 확인하지 않은 주장**

- **docstring의 가짜 예시:** 함수 사용 예시에 실제로 나온 적 없는 숫자("EX 0.53")를 썼다. Claude가 다시 읽다가 발견했고, 실제 실행 결과로 바꿨다.
- **문서의 사실 오류 (11/12, `docs/`):** 문서를 원문과 대조하다가 Claude가 찾아 고쳤다.
  - BIRD evidence 인용 문구가 원문(`refers MAX(...)`)과 달랐다(`refers to`).
  - `architecture.md`에 "판정을 다루는 곳은 모두 `match`와 `assert_never`를 쓴다"고 과장했다.
  - "`Literal`에 값을 더하면 한국어 설명 표에서 빠진 것을 pyright가 잡는다"고 썼다. 실제로 pyright는 딕셔너리 키가 다 있는지 검사하지 않는다.
  - `run-file.md`의 버전 정책을 거꾸로 썼다("그 버전의 도구로 다시 eval").
  - `cli.md`의 오류 예시에 실제와 다른 힌트 문구를 지어 넣었다.
  - 원본 스크립트로 확인하지 않은 BIRD 공식 예측 형식 변환법을 썼다(삭제).
- **확인하지 않은 근거 (11/11, `csv_safety.py`와 테스트):**
  - "전각 문자를 ASCII로 바꾸는 프로그램이 있어서 포함한다"
  - "앞에 공백이 있으면 엑셀이 수식으로 보지 않는다"
  - 둘 다 확인하지 않은 주장이라 확인한 출처(OWASP 목록)로만 설명하게 바꿨다.
- **숫자 착오 (11/12):** 공개 API 이름이 34개라고 보고했는데 실제로는 36개였다. Claude가 구현하면서 세어 보고 정정했다.

**규칙·설계의 실수**

- **SQL 강조 규칙의 가짜 강조 (11/11, `report/highlight.py`):** 계획대로 정규화만 했더니 같은 뜻의 SQL도 다르다고 칠했다.
  - 문제: 오답 165개 중 138개에서 FROM 절이 칠해졌다. `INNER JOIN`과 `JOIN`, 내부 조인의 순서, AND 조건의 순서 차이 때문이었다.
  - 발견: Claude가 실제 데이터로 강조 개수를 세다가 찾았다.
  - 조치: SQLite가 무시하는 쓰는 순서를 같게 보도록 더해서 77개로 줄였다. 계획과 달라진 점이라 사용자에게 보고하고 ADR 0039에 적었다.
- **공개 API에 빠진 타입 (11/12):** `Run.prediction_format`과 `CaseRecord.gold`·`.pred`의 타입 별칭이 `__all__`에 없었다. `api.md`를 쓰다가 Claude가 발견했고, 사용자에게 물어 추가했다.
- **빈 SQL에 `column_mismatch` (`facts/output.py`):** 예측이 없으면 컬럼이 0개라 "컬럼 수가 다름"이 붙었다. 컬럼이 0개면 세지 않도록 고쳤다.
- **집계식 안의 테이블 이름 (11/10, `facts/structure.py`):** `COUNT(bond.bond_id)`와 `COUNT(bond_id)`를 다르다고 보고했다. 비교할 때 테이블 이름을 떼도록 고쳤다.

**도구가 잡은 것**

- **Python 3.12 문법:** `def f[T: ...]`(PEP 695)를 두 곳(`_require`, `runfile.py`의 `_Reader.choice`)에 썼다. pyright와 Python 3.11 실행이 잡았고, `TypeVar`로 바꿨다.
- **`# type: ignore`와 근거 없는 우회:** 테스트에 여러 번 썼다(실행 파일·비교 테스트, 11/11 `test_highlight`, 11/12 e2e 초안). 자가 검토와 `reportUnnecessaryTypeIgnoreComment`가 잡았고, `dataclasses.replace`와 정확한 타입으로 바꿨다.
- **타입 별칭을 문자열로 쓴 코드 (11/11, `html_report.py`):** 작동하지 않는 코드였다. Claude가 다시 읽다가 발견해 바로 고쳤다.
- **sqlglot `Expression` (11/10):** pyright가 공개 이름으로 보지 않았다. `sqlglot.expressions.core.Expr`로 바꿨다.
- **CI에서만 실패한 재현성 테스트 (11/9, PR #8):** GitHub 서버가 느려서 247번 예측이 30초를 넘어 시간 초과가 됐다. 재현성 테스트가 판정 규칙이 아니라 기계 속도를 검사하고 있었던 것이다. 시간에 민감한 3개를 다시 실행하지 않고, 기록된 판정만 따로 고정했다.
- **환경 차이:** CI의 Python 버전마다 JSON 오류의 열 번호가 달라서 테스트가 줄 번호만 보게 했다. Hypothesis가 서로게이트 문자를 만들어서 UTF-8 문자로 제한했다. Windows BOM이 붙은 입력은 `utf-8-sig`로 읽게 했다.
- **느슨한 테스트 (11/12, `tests/test_docs.py`):** 실행 파일 문서 검사가 JSON 예시만 보고 통과했다. Claude가 문서를 일부러 망가뜨려 테스트가 실패하는지 확인하다가 발견했다. 검사를 엄격하게 바꾸자 설명이 빠진 필드 4개(`output`, `sql_structure`, `total`, `ex`)가 드러났다.
- **문구:** `must be a integer`, `has 1 lines`, `1 errors`를 고쳤다. `1 errors`는 CI 단계를 미리 돌려 보다가 발견했다.
- **파이프 끊김 (11/11):** `compare | head`처럼 출력을 중간에 끊으면 오류를 내고 `--max-drop` 실패의 종료 코드를 잃었다. 고쳤다.

## 배운 것

- **EX 숫자에 판정 규칙의 오류가 꽤 섞여 있다.** BIRD 공식 규칙으로 오답인 161개 중 38개(24%)가 거짓 오답 의심이었다. 동점 대체 정답이 있는 13문제 중 11개는 원래 정답과 결과가 다르다.
- **evidence는 주로 WHERE의 값을 알려 준다.** evidence를 빼면 `where_value`가 25개에서 132개로, `empty_result`가 34개에서 100개로 늘었다.
- **시간 제한이 있는 판정은 기계 속도에 따라 달라진다.** 재현성 테스트는 판정 규칙을 검사해야 하고, 하드웨어를 검사하면 안 된다.
- **규칙은 실제 데이터로 세어 봐야 한다.** 강조 규칙의 초안은 그럴듯했지만 실측에서 대부분이 가짜 강조였다.
- **테스트도 실패하는지 확인해야 한다.** 일부러 망가뜨려 보기 전까지 문서 검사가 느슨하다는 것을 몰랐다.
- **문서를 쓰면 설계의 구멍이 보인다.** API 문서를 쓰다가 공개 타입에서 빠진 이름을 찾았다.
- **도구에 대해 확인한 사실:**
  - uv_build는 모듈 폴더를 통째로 wheel에 넣는다.
  - Ruff 0.17은 Markdown 안의 Python 코드 블록까지 포맷 검사한다.
  - 엑셀은 `=`, `+`, `-`, `@`로 시작하는 CSV 셀을 수식으로 읽는다(OWASP CSV Injection).
