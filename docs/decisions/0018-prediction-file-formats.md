# 0018. 예측 파일은 한 줄 한 SQL 텍스트 파일과 자체 JSONL 두 형식을 받는다

- 날짜: 2026-11-08
- 상태: 채택
- 결정자: 사용자
- AI 관여: 선택지 조사·추천 (Claude 추천: 자체 JSONL만, 채택 여부: 부분 채택. 사용자가 텍스트 형식을 추가함)
- 관련 결정 ID: D27

## 맥락
사용자의 파이프라인(어떤 언어든)이 결과를 넘길 파일 형식을 정해야 했다. 0004에 따라 도구는 예측 파일만 받는다.

## 선택지
| 안 | 장점 | 단점 |
| --- | --- | --- |
| 자체 JSONL `{"id": ..., "sql": "...", "meta": {...}}` | 한 줄씩 덧붙이기 쉬움, 줄 번호로 오류 위치를 알려줄 수 있음, 케이스별 메타데이터를 담음 | 새 형식이라 사용자가 맞춰야 함 |
| BIRD 공식 형식 `{"0": "SQL\t----- bird -----\tdb_id"}` | BIRD 사용자가 가진 파일을 그대로 씀 | 파일 전체가 JSON 하나라 줄 번호가 없고 구분자를 파싱해야 함 |
| 둘 다 | 편리함 | 로더와 테스트가 두 배 |
| CSV (`id,sql`) | 엑셀·pandas로 만들기 쉬움 | SQL 안의 쉼표·따옴표·줄바꿈으로 깨지기 쉬움 |
| (사용자 추가) 한 줄에 SQL 하나인 텍스트 파일 | 연구에서 흔히 쓰는 형태(Spider 예측 파일 등), 만들기 가장 쉬움 | `id`가 없어 데이터셋 순서와 줄 순서로 짝을 맞춰야 함, SQL이 한 줄이어야 함 |

## 결정
두 형식을 받는다.
1. **텍스트 파일:** 한 줄에 한 줄짜리 SQL 하나. N번째 줄이 데이터셋의 N번째 케이스의 예측이다.
2. **자체 JSONL:** 한 줄에 JSON 객체 하나. 필수 필드 `id`, `sql`, 선택 필드 `meta`(객체).

BIRD 공식 형식은 계획대로 권장 범위에 둔다.

## 이유
추천안인 자체 JSONL에 더해, 한 줄에 SQL 하나인 텍스트 파일도 받기로 했다.

## 결과
- 텍스트 형식은 줄 수가 데이터셋 케이스 수와 다르면 오류로 처리한다. 빈 줄도 한 케이스(빈 예측)로 센다. 그래야 줄과 케이스의 짝이 어긋나지 않는다.
- JSONL은 `id`가 데이터셋에 없거나 중복되면 오류로 처리하고, 줄 번호를 알려 준다.
- 두 형식을 어떻게 구분할지(확장자 또는 CLI 옵션)는 CLI 결정(D14) 때 함께 정한다.
- 가이드 `prediction-format.md`에 두 형식의 예시를 모두 싣는다.
