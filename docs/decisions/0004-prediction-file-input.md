# 0004. 도구는 예측 파일을 입력으로 받고 LLM을 부르지 않는다

- 날짜: 2026-11-04 (기록: 2026-11-07)
- 상태: 채택
- 결정자: 사용자
- AI 관여: 선택지 조사·추천 (Claude 추천: 예측 파일 입력, 채택 여부: 예)
- 관련 결정 ID: D3

## 맥락
사용자의 연구 파이프라인은 Python과 bash로 만들었고, 단일 프롬프트부터 스키마 선택, 조인 경로 탐색, MCTS, agentic loop, 실행 기반 수정, 다중 후보 생성과 선택까지 구성이 계속 바뀌었다. 계획서 초판은 도구가 프롬프트를 소유하고 모델을 한 번 호출하는 구조였는데, 이 구조로는 실제로 평가하던 파이프라인을 담을 수 없다.

## 선택지
| 안 | 장점 | 단점 |
| --- | --- | --- |
| 도구가 LLM을 호출 (초판) | 한 명령으로 생성부터 채점까지 | 다단계 파이프라인을 담기 어려움, Provider·캐시·API 키 관리 등 범위가 커짐 |
| 예측 파일을 입력으로 받음 | 어떤 언어·구조의 파이프라인이든 결과만 넘기면 됨, BIRD 공식 평가 방식과 같음, 범위가 크게 줄어듦 | 생성 단계는 사용자가 따로 돌려야 함 |

## 결정
도구는 `predictions.jsonl`(케이스별 최종 SQL)을 입력으로 받아 판정과 분석만 하고, LLM을 호출하지 않는다.

## 이유
추천한 구조를 채택했다. 결과 파일을 LLM이 읽고 분석하는 beta 기능은 지금 만들지 않고 로드맵에만 둔다.

## 결과
- Provider 어댑터, 프롬프트 템플릿, 응답 캐시·replay, mock 모델, API 키 처리를 도구 본체에서 뺀다.
- 시연용 예측은 `examples/baseline`의 별도 스크립트가 만든다(D24).
- "결과 파일을 LLM이 읽고 분석을 제안하는 beta"는 로드맵에 둔다(0008). 그때도 사실 추출 자체는 결정적으로 유지한다.
