# 0010. 프로젝트 관리는 uv, 빌드 백엔드는 uv_build로 한다

- 날짜: 2026-11-07
- 상태: 채택
- 결정자: 사용자
- AI 관여: 선택지 조사·추천 (Claude 추천: uv + uv_build, 채택 여부: 예). 사용자가 도구를 잘 모른다고 밝혀 추천을 따른 결정이다.
- 관련 결정 ID: D9
- 편집: 2026-11-15, 공개 전에 프로젝트와 무관한 개인 정보를 지움([0047](0047-remove-unrelated-personal-content.md))

## 맥락
의존성 설치, 잠금 파일, 가상환경, Python 버전, 패키지 빌드를 어떤 도구로 관리할지 정해야 했다. 빌드·의존성 설정이 깔끔하고, 같은 환경을 다시 만들 수 있어야 한다.

## 선택지
| 안 | 장점 | 단점 |
| --- | --- | --- |
| uv + uv_build | 설치·잠금 파일·Python 버전 관리·빌드를 한 도구로 처리, 빠름, uv_build 0.13.7은 Production/Stable | 순수 Python만 빌드 가능(이 프로젝트는 해당 없음), uv_build 버전 상한을 걸어야 함 |
| uv + hatchling | 널리 쓰이는 백엔드, 기능이 많음 | 이해할 도구가 하나 늘어남 |
| Poetry 2.x | 성숙함 | 별도 명령 체계, 상대적으로 느림 |
| pip + venv | 추가 도구 없음 | 표준 잠금 파일이 없어 재현성이 약함 |

## 결정
uv로 프로젝트를 관리하고 `uv.lock`을 커밋한다. 빌드 백엔드는 `uv_build`이고, 공식 문서 권장대로 다음 minor 버전 미만으로 상한을 건다.

## 이유
추천안(uv + uv_build)을 채택했다.

보충: 사용자는 도구를 잘 모른다고 밝혔다. 이 결정은 Claude의 추천을 따른 것이고, 직접 설명할 수 있도록 uv의 역할(가상환경, 잠금 파일, `uv run`, 빌드)을 `/explain`으로 학습해야 한다.

## 결과
- 설치는 `uv sync`, 실행은 `uv run`, 빌드는 `uv build`로 한다.
- CI는 Astral의 공식 GitHub Action으로 uv를 설치하고, uv 버전을 고정한다.
- uv와 uv_build의 버전 정책이 바뀌면 상한을 다시 본다.
