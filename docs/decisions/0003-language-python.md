## 맥락
계획서 초판은 TypeScript를 골랐다. 그러나 사용자는 TypeScript를 써 본 적이 없고, 대표 기능(오답 사실 추출, 0005)은 SQL 파싱·정규화 라이브러리의 품질에 크게 좌우된다.

## 선택지
| 안 | 장점 | 단점 |
| --- | --- | --- |
| TypeScript | 언어 자체의 정적 타입으로 타입 설계를 보여 줌 | 사용자가 처음 쓰는 언어, SQL 정규화 생태계가 약해 직접 만들어야 할 부분이 많음, 모든 줄을 설명하기 어려움 |
| Python | 사용자가 익숙함, sqlglot 등 방언 파싱·정규화 도구가 성숙함, 사용자층(text-to-SQL 연구자)과 BIRD 공식 평가 스크립트가 Python | 타입 검사를 별도 도구(pyright 등)로 해야 함 |

## 결정
Python으로 구현한다.

## 이유
TypeScript를 꼭 써야 할 이유는 없다고 보고 Python을 골랐다.

보충: 타입을 정확하게 쓰려는 고민은 Python의 strict 타입 검사, `Literal` 기반 판별 유니언, `py.typed` 배포로 보여준다.

## 결과
- 패키지는 `src/text2sql_eval/` 하나로 둔다.
- 타입 검사기 strict 모드 0 오류를 완료 기준에 넣는다(타입 검사기는 D11에서 정함).
