# 0039. HTML 리포트 범위: 기본 화면과 차이 강조

- 날짜: 2026-11-11
- 상태: 채택
- 결정자: 사용자
- AI 관여: 선택지 조사·추천 (Claude 추천: 기본, 채택 여부: 아니오)
- 관련 결정 ID: D37

## 맥락
계획서의 HTML 기능은 여러 개다. SQL 자동 정렬과 나란히 보기, 다른 절 강조, 결과 표 차이, 필터, 비교 화면이 있다. 리포트는 11/12 하루에 끝내야 하고, 범위 점검 3 규칙은 결과 표 차이 표시를 뺄 수 있다고 정해 두었다. 그래서 무엇을 넣을지 정해야 했다.

## 선택지
| 안 | 장점 | 단점 |
| --- | --- | --- |
| 기본: 요약 + 오답 목록 + 필터 + 케이스 상세 (질문, evidence, 자동 정렬된 정답·예측 SQL 나란히, 출력 차이, 구조 차이 근거, 플래그, 결과 앞부분 표 나란히) | 하루에 확실히 끝남, 연구 때 엑셀로 보던 정보가 다 있음 | 다른 부분을 눈으로 찾아야 함 |
| 기본 + 강조: 위에 더해 SQL에서 다른 절, 결과 표에서 다른 행을 색칠 | 다른 부분을 찾는 시간이 줄어듦 | 일정 위험 |
| 기본 + `compare` HTML | 두 실행 비교도 화면으로 봄 | 일정 위험, 계획서에서 권장 범위 |

## 결정
기본 화면에 더해, SQL에서 다른 절과 결과 표에서 다른 행을 강조한다. `compare` HTML은 만들지 않는다.

## 이유
> "D37: 기본+강조."

Claude는 구조 차이의 근거 조각이 같은 화면에 보여 강조와 효과가 겹친다며 기본을 추천했다. 사용자는 강조까지 넣기로 했다.

## 결과
- 강조는 표시일 뿐이고, 판정·출력 차이·구조 차이·플래그를 바꾸지 않는다. 출력 차이와 같은 범위(정답이 아니고 정답 SQL이 실행된 케이스)에만 강조한다.
- SQL 강조 규칙 (구현 계획 승인, 2026-11-11):
  - 바깥 쿼리를 절 단위(WITH, SELECT, FROM+JOIN, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT+OFFSET)로 나눈다.
  - 구조 차이와 같은 정규화(별칭→테이블 이름, 식별자 소문자, 컬럼 앞 테이블 이름 제거)를 한 뒤 같은 절끼리 비교한다. 다르거나 한쪽에만 있는 절을 양쪽에서 칠한다. SELECT의 `AS` 별칭은 EX와 상관없으므로 비교에서 뺀다.
  - SQLite가 무시하는 쓰는 순서도 차이로 보지 않는다. AND로 이은 조건의 순서, `=` 양쪽의 순서, 내부 조인의 순서, `INNER JOIN`과 `JOIN`이 해당한다. JOIN의 ON 조건은 어느 테이블끼리 잇는지가 중요하므로 테이블 이름을 남긴다. 이 규칙은 계획 승인 뒤 실측에서 가짜 강조가 많아 더했다. evidence 있음 실행의 오답 165건에서 FROM 강조가 138건에서 77건으로 줄었다(`tables_joins` 구조 차이는 72건).
  - 어느 한쪽이 비었거나 파싱에 실패했거나 바깥이 SELECT가 아니면(UNION 등) 강조하지 않는다.
- 결과 표 강조 규칙: 상대 결과에 없는 행을 칠한다. 실행 파일에는 결과 앞 20행만 있으므로, 상대 결과가 전부 저장된 경우(20행 이하)에만 칠한다. 컬럼 수가 다르면 칠하지 않는다. 값은 EX처럼 비교한다(`1 == 1.0`).
- SQL 자동 정렬은 이미 쓰는 sqlglot의 `pretty` 출력을 쓴다. 새 의존성은 없다.
- 범위 점검 3(11/12 밤)에서 리포트가 끝나지 않으면 강조를 먼저 뺀다. CSV는 줄이지 않는다.
- `compare` HTML은 로드맵에 남긴다. 비교는 터미널 요약과 `compare --csv`로 본다.
