# 0032. SQL 파서는 sqlglot을 쓴다

- 날짜: 2026-11-10
- 상태: 채택
- 결정자: 사용자
- AI 관여: 선택지 조사·추천과 파싱 확인 (Claude 추천: sqlglot, 채택 여부: 예)
- 관련 결정 ID: D15

## 맥락
구조 사실(0031)을 내려면 정답·예측 SQL을 파싱해 테이블, WHERE 조건, 집계, ORDER BY/LIMIT을 꺼내야 한다. 언어를 Python으로 정한 이유 중 하나가 SQL 파싱 생태계였다(0003).

## 선택지
| 안 | 장점 | 단점 |
| --- | --- | --- |
| sqlglot 30.31.0 | 방언별 파서(SQLite 포함), AST 탐색 API, 정규화·최적화 모듈, MIT, 의존성 0개 | 큰 라이브러리, 버전이 빨리 바뀜 |
| sqlparse | 가볍고 오래됨 | 토큰 수준이라 AST가 없어 조건·테이블 추출을 직접 해야 함 |
| 직접 작성 | 의존성 0개 | 서브쿼리·CTE까지 다루기엔 일정 밖 |

## 결정
`sqlglot`을 런타임 의존성으로 추가하고 `read="sqlite"`로 파싱한다.

## 이유
추천안(sqlglot)을 채택했다.

보충: 2026-11-10 baseline 두 실행의 SQL 1,728개 중 1,727개를 파싱했다. 유일한 실패는 백슬래시 이스케이프가 섞인 깨진 쿼리로, SQLite도 거부한다.

## 결과
- `pyproject.toml`의 `dependencies`에 `sqlglot`을 넣고 `uv.lock`에 고정한다. 런타임 의존성은 1개가 된다.
- 파싱 실패는 예외가 아니라 "구조 사실 없음, 이유: 파싱 실패"로 기록한다.
- PostgreSQL·MySQL 방언은 파서가 지원하므로 로드맵의 다른 DB 지원 때 `read` 인자만 바꾸면 된다.
