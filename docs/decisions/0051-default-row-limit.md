# 0051. 결과 행 수는 기본으로 1,000,000행까지만 받는다

- 날짜: 2026-11-20
- 상태: 채택
- 결정자: 사용자
- AI 관여: ponytail 점검(0049)에서 메모리 사용량을 실측하고 선택지 추천 (Claude 추천: 기본 1,000,000행, 채택 여부: 예)
- 관련 결정 ID: D47

## 맥락
ADR 0021은 행 수 제한의 기본값을 두지 않았다. 점검에서 조인 조건이 빠진 예측(예제 DB의 `superhero × hero_power`)이 6.7초 만에 437만 행을 내고 메모리를 1.4GB 썼다. 판정 결과 파일은 모든 쿼리가 끝난 뒤 한 번 쓰므로, 메모리가 바닥나면 그때까지의 판정을 모두 잃는다. 제한은 정답 SQL에도 걸린다. 예제 데이터에서 정답 결과가 가장 큰 것은 21,056행이다.

## 선택지
| 안 | 장점 | 단점 |
| --- | --- | --- |
| 기본 1,000,000행 | 쿼리 하나의 메모리를 약 300MB로 묶음(예제 DB 실측 기준), 정답 결과보다 충분히 커서 공식 스크립트와 판정이 거의 달라지지 않음 | 큰 쿼리 여러 개가 동시에 돌면 몇 GB를 쓸 수 있음 |
| 기본 100,000행 | 메모리가 그 10분의 1 | BIRD 전체에서 정답 결과가 10만 행을 넘으면 공식 스크립트와 EX가 달라짐 |
| 제한 없음 유지, 문서에 경고 | 공식 스크립트와 똑같음 | 메모리 부족으로 평가가 죽는 일이 그대로 남음 |

## 결정
`--max-rows`(Python에서는 `max_rows`)의 기본값을 1,000,000으로 한다. 결과가 이보다 많으면 지금처럼 `row_limit` 실행 오류(0점)로 기록한다. 0021의 "행 수 제한: 기본값은 없음"을 대체한다.

## 이유
추천안(기본 1,000,000행)을 채택했다. 쿼리 하나의 메모리를 묶으면서도 정답 결과 크기보다 충분히 커서, 공식 스크립트와 판정이 달라질 일이 거의 없다.

## 결과
- 기본값은 `execution/executor.py`의 `DEFAULT_MAX_ROWS` 한 곳에서 정한다. `execute_query`, `execute_all`, `evaluate`, `evaluate_files`, CLI가 이 값을 함께 쓴다.
- Python에서 `max_rows=None`을 주면 제한이 없다. CLI에서는 `--max-rows`에 더 큰 수를 준다.
- 정답 결과가 100만 행을 넘으면 정답 쪽 실행 오류가 되어 공식 스크립트와 EX가 달라진다. 결과 읽기 가이드에 이 경우를 적는다.
- BIRD dev 전체에서 정답 결과의 최대 행 수는 확인하지 않았다. 확인해서 100만 행에 가까운 정답이 있으면 이 결정을 다시 본다.
- 커밋된 예제 실행 파일은 제한 없이 만들었으므로 `max_rows: null`로 남는다. 가장 큰 결과가 21,056행이라 판정은 같다.
- 0021의 상태를 "일부 대체됨(0051)"로 바꾼다.
